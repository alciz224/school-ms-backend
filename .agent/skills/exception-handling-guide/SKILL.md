# Exception & Error Handling Guide

This project strictly separates HTTP error responses from domain logic. **Never return raw HTTP 400 or 500 Responses from views**; instead, raise the appropriate `DomainException` in your services, selectors, or serializers. The project's `custom_exception_handler` will automatically catch these and format them into a consistent JSON shape for the frontend.

## 1. The Standard Error Response
Every error generated by the backend MUST follow this exact JSON structure:
```json
{
    "success": false,
    "error": {
        "code": "error_code_string",
        "message": "Human readable message.",
        "details": { ... },
        "field_errors": { ... } // Optional, only for validation errors
    }
}
```
The frontend expects this shape to display toast notifications and attach errors to specific form fields.

## 2. The Core Domain Exceptions
All custom exceptions live in `domain/shared/exceptions.py`. You should always import and raise these instead of standard Python exceptions or DRF exceptions when dealing with business logic:

### `ValidationException` (HTTP 400)
Used when input data violates business rules or formatting requirements.
```python
from domain.shared.exceptions import ValidationException

raise ValidationException(
    message="Invalid school schedule.",
    code="invalid_schedule",
    field_errors={"start_time": ["Must be before end time."]}
)
```

### `NotFoundException` (HTTP 404)
Used when a requested resource does not exist.
```python
from domain.shared.exceptions import NotFoundException

raise NotFoundException(
    resource_type="School",
    resource_id=school_id
)
```

### `ConflictException` (HTTP 409)
Used for uniqueness violations or state conflicts.
```python
from domain.shared.exceptions import ConflictException

raise ConflictException(
    field="code",
    value="LYC-123",
    message="This school code is already in use."
)
```

### `BusinessRuleException` (HTTP 422)
Used when an action violates a core domain or business rule (e.g., trying to activate an already active school).
**Important:** Pass the rule identifier via the `rule` argument. It is automatically stored in the `details` dictionary.
```python
from domain.shared.exceptions import BusinessRuleException

raise BusinessRuleException(
    rule="school_already_active",
    message="Cannot activate a school that is already active."
)
```

### `PermissionDeniedException` (HTTP 403)
Used when the user is authenticated but lacks permission for the specific resource.
```python
from domain.shared.exceptions import PermissionDeniedException

raise PermissionDeniedException(
    action="delete",
    resource="SchoolYear"
)
```

## 3. Django and DRF Exception Fallbacks
The `custom_exception_handler` also intercepts native exceptions:
- **`django.core.exceptions.ValidationError`**: Caught and converted to `ValidationException` with field-level errors automatically.
- **`django.http.Http404`**: Caught and converted to `NotFoundException`.
- **DRF `ValidationError`**: Caught and wrapped in the standard `{"success": False, "error": {...}}` shape.

## 4. Key Takeaways for Agents
1. **Never suppress errors silently.** Always raise explicit exceptions so the frontend knows exactly why an operation failed.
2. **Provide detailed field errors.** If a form submission fails, map the errors directly to the fields the frontend sent using `ValidationException(field_errors={...})`.
3. **Use explicit codes.** Pass a unique snake_case `code` (e.g., `invalid_transition`) so the frontend can programmatically translate or handle the error, instead of relying on parsing the string `message`.
